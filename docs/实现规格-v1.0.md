## 2. 目标与非目标

### 目标

让《影之一族》达到「用户可演示、可交付的 v1」。
v1 的定义：`main` 上一个干净的提交，编译零错误，全量 EditMode 全绿，场景 Validator 零错误，Play Mode 能走完「标题 → 选剧本 → 营地 HUD → 月结 → 一次家主更替」，存读档在同一次会话内往返一致。

### 非目标

以下不属于 v1，也不在本规格的任务清单里。
大型开放世界、完整战国地图、复杂战术 AI、忍术动画、几十种产业、数百完整 NPC、完整战争、多人。
战术系统的正式投入（checkpoint 1.15 规定须在 M05 验收后）。
重写模拟内核、替换存档框架、升级 Unity 版本。
合并 `main` 之外的任何历史改写。
SC-014、SC-015、SC-016 三条跨代链补代码。它们现在只有事件目录与中文文本，引擎按现有允许列表就能承载。v1 验收不依赖它们，也不为它们写新运行时。
CI 与打包脚本。仓库没有 CI 也没有打包脚本，本机没有 .NET SDK，唯一构建路径是已开的 Editor 加 Pipeline bridge。v1 只在 T16 里验一次发行构建的入口，不建流水线。
视觉打磨。按 D5 走，字号行高、5 项 UI 决定、美术补齐都不进 v1。
PlayMode 自动化。`Assets/Tests/PlayMode` 是空目录，v1 的运行时验证靠 Play Mode 手工驱动配方，不补自动化。

## 3. 最终形态与可感知完成标准

玩家打开工程进 Play Mode，以下七条同时成立，即为 v1 完成。每条都能由人眼在屏幕上看出来，不需要读代码。

1. 标题页出现「影之一族」与「守护家名，传承百年」，有「继续游戏」与「开始新游戏」。
2. 选「固定三代剧本（SC-013）」后进入营地 HUD，顶部读到 `1560 年 4 月 1 日`，所在地 `清洲`。
3. 点「结束月份」后日期推进到下月 1 日，资金、物资、人口有可读变化，控制台零新增 error。
4. 家族名册里每人有身份、能力与关系，编年史面板能读到已发生的事件。
5. 触发一次家主更替，新家主接任后世界、关系、家业不重置，编年史有交接记录。
6. 存档按钮后状态行离开 `未存档`，推进一天后读档，日期与人数回到存档时。
7. 城镇页能列出当地可办的委托，点一条能打开对应任务页。

## 5. 数据与内容结构（接入点）

命名约定：类型与成员用英文 PascalCase，游戏内文案用中文常量，稳定 ID 形如 `person.sc022.head`、`chain.sc013.family-letters`、`market.food`。

### 5.1 程序集与依赖方向

`SengokuChronicle.Domain`（纯 C# 规则核，无引用）、`SengokuChronicle.Events`（事件目录与允许列表引擎）、`SengokuChronicle.Persistence`（版本化 DTO 与原子存储）、`SengokuChronicle.Application`（`GameSession` 是唯一编排点）、`SengokuChronicle.Presentation`（uGUI，只显示与转发输入）、`SengokuChronicle.Editor`（事务式场景生成器与 Validator）、`SengokuChronicle.EditModeTests`。
依赖方向 `Presentation → Application → Domain/Events`，`Application ↔ Persistence` 只经显式 DTO 映射。Domain 与 Events 不引用场景对象。
新增玩法规则落在 Domain 的纯 C# 类，接口留在 Application，界面在 Presentation。这条决定了任何新条目的文件落点。

### 5.2 存档与隔离槽

- 结构版本 `saveFormatVersion = 17`，规则版本 `rulesVersion = 8`。两个号分开管，结构变更才升前者。
- `SaveSlotStore` 定义在 `Assets/Scripts/Persistence/SaveSlotStore.cs`。构造 `new SaveSlotStore(string directory)`，常量为 `FileName = "save-slot-1.json"`、`BackupFileName = "save-slot-1.json.bak"`。实例暴露 `DirectoryPath`、`FilePath`、`BackupFilePath`、`Exists()`。
- 默认槽位由 `SaveSlotStore.CreateDefault()` 给到 `Application.persistentDataPath/SengokuChronicle`，那是用户真实存档，任何验证都不得写入。
- 会话入口 `GameSession.SaveTo(SaveSlotStore)` / `LoadFrom(SaveSlotStore)`，在 `Assets/Scripts/Application/GameSession.cs:2914` 与 `:2933`。
- 注入点两处，必须同时重定向，否则「继续游戏」仍会写真实槽：`SaveLoadPanel.SetStore(SaveSlotStore)`（`Assets/Scripts/Presentation/SaveLoadPanel.cs:76`）与 `TitleScreenController.SetStore(SaveSlotStore)`（`Assets/Scripts/Presentation/TitleScreenController.cs:244`）。
- 已成型的隔离配方在 `Logs/verify/gate-20261118/IsolateSaveStore.cs`，提供 `Set()`、`Probe()`、`AdvanceOneDay()`、`RealSaveFingerprint()`。`Set()` 会拒绝在已有槽位数据的目录上工作，这是有意的保护。

### 5.3 城镇活动条目

- 契约在 `Assets/Scripts/Presentation/TownLocalActions.cs`。
- `enum Kind` 五项，顺序即展示顺序：`SupplyShortage`、`SealedLetter`、`MarketTally`、`EscortCommission`、`TacticalMission`。
- `readonly struct Entry { Kind Kind; string Label; }`。
- 三个只读入口：`GetAvailable(GameSession)` 返回 `IReadOnlyList<Entry>`，`Describe(GameSession)` 返回多行块，`DescribeCompact(GameSession)` 返回两行摘要。文案常量 `Header = "当地委托"`、`Empty`、`Unavailable`。
- 每个 `Add*` 方法复述一个既有的领域门禁，不新增规则、资源、路线或存档字段。改这里等于改界面文案，不是加玩法。
- 界面挂在与 `Assets/Scripts/Presentation/TownOverviewPanel.cs` 的 `TownActivityButtons` 子节点上，由 `Assets/Scripts/Editor/UpdateTownOverview.cs` 生成。路由入口是 `WorldMapController.OpenTownActivity(TownLocalActions.Kind)`（`Assets/Scripts/Presentation/WorldMapController.cs:755`）。

### 5.4 场景与生成器

- 唯一长期场景 `Assets/Scenes/FoundationScene.unity`。
- 场景改动只走事务式 updater。每个 updater 只认精确的旧层级，遇其他形状直接拒绝，可重复执行，异常走 Undo 回滚且不重载场景。
- 根路径固定，例如 `Canvas/M6TitleRoot`、`Canvas/M02DailyActionRoot`、`Canvas/M2WorldMapRoot/M5SaveLoadRoot`、`Canvas/SuccessionRoot`、`Canvas/TownOverviewRoot/TownActivityButtons`。
- 不手改 `.unity` 与 `.prefab` 的 YAML。
- 生成后必须跑 `FoundationSceneValidator`，报告写 `Logs/SceneValidationReport.txt`。

## 8. 风险与回退

| 风险 | 应对 |
|---|---|
| 场景冲突。`FoundationScene.unity` 在 main 与四个工作树都被改过，三方合并 YAML 会产出大面积无意义差异 | 场景不参与合并。只合并代码，然后在 main 侧重放 updater 并用 `FoundationSceneValidator` 复验。回退靠 `git revert -m 1 <merge-sha>` |
| 合并后发现回归 | 每次合并后立刻跑全量 EditMode。失败先 `revert` 合并，再在分支上修 |
| 测试证据被覆盖。多个工作树共用同一份测试结果文件 | 一次只在一个工作树上跑测试，不并行。每次跑完把结果文件复制到 `Logs/verify/<stamp>/` |
| `run_tests` 客户端超时制造假 error | 用 `--detach` 提交，然后轮询 `test_status`。客户端断开产生的两条 pipeline 传输 error 必须从「新增 error」里剔除 |
| 截图是陈旧帧 | 每次 `capture_game_view` 前先 `editor_focus`，等 2 至 5 秒，用 md5 校验确认是新帧再目视。截图放 `Assets/Logs/verify/_scratch/`，看完立即删除 |
| 写坏用户真实存档 | 验证一律走隔离目录。第 5.2 节的两个注入点必须同时重定向。每轮前后对比 `RealSaveFingerprint()` |
| Editor 被误操作 | 开工前 `unity pipeline list` 核对 PID 与 `-projectPath`。绝不对被占用的工程目录跑 batchmode。不按进程名杀 Editor |
| 长期模拟结论被当成通过 | 写作口径固定为「当前基线」，附种子数与策略 ID，不写生存率结论 |
| Editor 卡在模态对话框 | `editor_status` 报 `blocked_by_dialog` 时停下，说明是哪个对话框，不要绕过 |
| 同一 workspace 有多个 agent 并发写 | 这个目录同时跑着 5 个任务，本文写作期间 `checkpoint.md` 就被同批 worker 改过。落笔前先读最新内容再改，不要用旧内容整文件覆盖 |

## 附录 B 证据文件格式

一份证据一个文件，`Logs/verify/<stamp>-<feature>.md`。必须包含：跑的是哪个分支与哪个提交、执行过的命令按顺序、`editor_status` 前后值、Console 计数（注明取自 `counts` 还是 `groundTruth`，两者当前差 1）、被测值的前后读回、最后一行判定 `PASS` / `FAIL` / `BLOCKED` 加理由。
编译、EditMode、场景 Validator、Console、Play Mode、用户验收是六类独立证据，互不替代。宿主侧脚本结果不算 Unity 运行证据。
